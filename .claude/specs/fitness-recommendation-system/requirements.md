# 基于机器学习的健身计划推荐系统 — 需求规格说明书

> 题目：基于机器学习的健身计划推荐系统设计与实现
> 版本：v1.0（初稿）
> 依据：邹家辉开题报告 0825
> 说明：本文档采用 EARS（Easy Approach to Requirements Syntax）编写验收标准。

---

## 1. 项目概述

面向普通个人健身用户，构建一套 Web 指导系统。用户录入 9 项身体与习惯特征后，系统基于随机森林（Random Forest）多分类模型，输出 6 类健身计划推荐结果；并依据训练完成率、体重变化趋势、主观疲劳评分与训练反馈，对下一周期计划进行动态调整。系统同时提供训练记录管理、身体指标趋势可视化与训练效果评估。

技术边界：前端 Vue 3（SPA）+ ECharts，后端 Python FastAPI + SQLAlchemy，数据库 MySQL，模型 scikit-learn（Random Forest + SMOTE + GridSearchCV），数据源为 Kaggle 三套健身数据集 + 本土化问卷。

|------|------|------|

## 3. 核心数据定义

### 3.1 9 个输入特征（用户画像）

| # | 中文名 | 字段名 | 类型 | 取值范围 / 编码 |
|---|--------|--------|------|------------------|
| 1 | 性别 | `gender` | 分类 | 0=男，1=女 |
| 2 | 年龄 | `age` | 数值 | 14–70 岁 |
| 3 | 身高 | `height_cm` | 数值 | 140–210 cm |
| 4 | 体重 | `weight_kg` | 数值 | 35–200 kg |
| 5 | 运动目标 | `goal` | 分类 | 减脂 / 增肌 / 塑形 / 提升耐力 / 保持健康 |
| 6 | 运动基础 | `experience_level` | 分类 | 新手 / 初级 / 中级 / 高级 |
| 7 | 每周可用时间 | `weekly_hours` | 数值 | 1–21 小时/周 |
| 8 | 饮食偏好 | `diet_preference` | 分类 | 均衡 / 高蛋白 / 低碳水 / 低脂 / 素食 |
| 9 | 运动伤病 | `injury` | 多标签（多选） | 无 / 膝 / 腰 / 肩 / 腕 / 踝 / 其他；「无」与其他选项互斥 |

> BMI 由身高、体重推导：`bmi = weight_kg / (height_cm / 100)^2`，作为派生特征进入模型，不单列为用户输入。

### 3.2 6 类推荐输出

| # | 中文名 | 字段名 | 类型 | 取值说明 |
|---|--------|--------|------|----------|
| 1 | 训练目标 | `target_goal` | 分类 | 减脂 / 增肌 / 塑形 / 提升耐力 / 保持健康 |
| 2 | 每周训练频率 | `weekly_frequency` | 数值 | 2–6 次/周 |
| 3 | 动作组合 | `exercise_plan` | 列表 | `[{name, sets, reps}]` 动作×组数×次数 |
| 4 | 单次训练时长 | `session_duration_min` | 数值 | 20–90 分钟 |
| 5 | 训练强度等级 | `intensity_level` | 分类 | 低 / 中 / 高 |
| 6 | 训练周期 | `training_cycle_weeks` | 数值 | 4–12 周 |

### 3.3 动态调整依据

| 依据 | 字段名 | 类型 | 说明 |
|------|--------|------|------|
| 训练完成率 | `completion_rate` | 数值 0–1 | 实际完成 / 计划应完成 |
| 体重变化趋势 | `weight_trend` | 派生 | 由体重记录序列计算 |
| 主观疲劳评分 | `fatigue_score` | 数值 1–10 | RPE 主观疲劳 |
| 训练反馈 | `feedback` | 文本/枚举 | 如「太轻松 / 适中 / 太累」 |

## 4. 用户故事与验收标准

### US-1：用户注册与登录

**As a** 普通健身用户
**I want** 注册账号并登录系统
**So that** 我的画像、推荐与训练记录得以持久化，跨设备可访问

**Acceptance Criteria (EARS)**

1. WHEN 用户提交注册表单（用户名、密码）
   THE SYSTEM SHALL 校验用户名唯一性与密码强度（≥6 位）并创建账户。
2. WHEN 用户使用有效凭证登录
   THE SYSTEM SHALL 校验密码并签发 24 小时有效的 JWT。
3. WHEN 用户提交错误凭证
   THE SYSTEM SHALL 返回「用户名或密码错误」且不泄露具体是哪个字段错误。
4. THE SYSTEM SHALL 以加盐哈希（bcrypt）存储密码，不以明文保存。

### US-2：用户画像录入

**As a** 普通健身用户
**I want** 录入我的 9 项身体与习惯特征
**So that** 系统能据此生成个性化健身计划

**Acceptance Criteria (EARS)**

1. WHEN 用户提交画像表单
   THE SYSTEM SHALL 校验 9 项特征的取值合法性（见 3.1 取值范围）。
2. WHEN 存在缺失或越界的字段
   THE SYSTEM SHALL 在对应字段下方展示内联错误，不刷新页面。
3. WHEN 用户更新画像
   THE SYSTEM SHALL 保存新版本并标记旧推荐结果待重算。

### US-3：健身计划智能推荐

**As a** 普通健身用户
**I want** 一键获取 6 类推荐结果
**So that** 无需专业知识即可得到可落地的训练方案

**Acceptance Criteria (EARS)**

1. WHEN 用户请求生成推荐
   THE SYSTEM SHALL 读取最新画像，调用随机森林模型，返回 6 类结果（训练目标、频率、动作组合、时长、强度、周期）。
2. WHEN 推荐成功生成
   THE SYSTEM SHALL 持久化推荐记录并附上模型版本号。
3. WHEN 模型尚未加载或推理失败
   THE SYSTEM SHALL 返回友好错误信息而非 500 崩溃。

### US-4：训练记录管理

**As a** 普通健身用户
**I want** 打卡并记录每次训练
**So that** 我能追踪执行情况，系统能据以动态调整

**Acceptance Criteria (EARS)**

1. WHEN 用户提交一次训练打卡
   THE SYSTEM SHALL 记录日期、完成率、疲劳评分与反馈。
2. WHEN 用户查询历史记录
   THE SYSTEM SHALL 按时间倒序返回训练记录列表。

### US-5：动态调整建议

**As a** 普通健身用户
**I want** 系统根据我的执行反馈调整下一周期计划
**So that** 计划随身体状态变化而自适应

**Acceptance Criteria (EARS)**

1. WHEN 某训练周期结束且存在 ≥3 条打卡记录
   THE SYSTEM SHALL 综合完成率、体重趋势、疲劳评分，生成下一周期频率与强度的调整建议。
2. WHEN 完成率持续偏低或疲劳评分持续偏高
   THE SYSTEM SHALL 给出降频或降强度建议。

### US-6：数据可视化

**As a** 普通健身用户
**I want** 直观查看运动完成情况与体重趋势
**So that** 我能快速评估训练效果

**Acceptance Criteria (EARS)**

1. WHEN 用户进入仪表盘
   THE SYSTEM SHALL 用图表展示训练完成率趋势与体重变化趋势。
2. WHEN 用户切换时间范围（周/月）
   THE SYSTEM SHALL 按所选范围刷新图表数据。

## 5. 非功能需求（NFR）

| 类别 | 需求 |
|------|------|
| 性能 | 推荐 API 在 95 分位 ≤ 500ms；前端首屏可交互 ≤ 2s |
| 模型质量 | 训练集 ≥ 89000 条可用样本；以加权 F1（非单纯准确率）评估 |
| 安全 | 密码 bcrypt 哈希；JWT 鉴权；CORS 白名单；SQLAlchemy 参数化查询防注入 |
| 可维护 | 前后端分离；Pydantic 数据模型；FastAPI 自动 Swagger 文档 |
| 数据质量 | 去重、异常过滤、缺失填充、特征标准化、SMOTE 平衡类别 |

## 7. 已确认决策（2026-10-09）

1. 运动伤病 `injury` → **多选（多标签）**，「无」与其他部位互斥。
2. 动作库 `exercise_plan` → **独立字典表**（exercise 动作字典表 + plan_template 计划模板表），可后台维护。
3. 问卷采集 → **问卷星导出 CSV**，选项编码与 9 特征字典一致。
4. 管理员角色 → **v1 启用最小管理员**（用户列表 + 模型版本查看）。
5. 开发约定 → **每个任务完成后执行一次 git 提交**；**前端开发使用提供的 frontend-design / frontend-skill**。
